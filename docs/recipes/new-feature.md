# Recipe: explore a new feature

## Situation

Someone has proposed a feature, but you are not yet sure whether the proposed solution is the right way to improve the underlying situation.

For example:

> We should add AI summaries to support tickets.

## Start with

```text
/discover We should add AI summaries to support tickets.
```

## What to expect

ITP should separate the feature from the underlying need before investing deeply in the solution. It may ask what users are trying to accomplish, what is difficult today, what workaround exists, and what observable change would actually count as improvement.

It should then explore genuinely different approaches, including an existing capability or a smaller intervention when those are credible. It should research only the assumptions that could materially change the choice.

Eventually, it should present the real alternatives as a simple list that explains what each option means, why you might choose it, and its main downside. It should then recommend the strongest option or small shortlist and explain the recommendation before asking the human to choose.

## Healthy result

You might still choose the original feature. The important difference is that you now understand **why** it is worth doing and what outcome it is supposed to produce.

Or you may discover that a smaller solution, existing feature, experiment, or no-build decision is better.

If you pursue, the final ITP output is an exact approved promise—not an implementation plan.
